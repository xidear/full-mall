# 秒杀两种形态与并发设计

## 1. 两种形态（业务口径，用户 2026-10-19 明确）

| 形态 | 特征 | 系统要求 |
|---|---|---|
| **真秒杀** | 少量低价商品、到点瞬时抢购、**不许超卖** | 原子扣减、限购、削峰、可观测 |
| **营销型秒杀** | 名义秒杀、价格不高、时间窗内持续有货 | 活动价生效即可，不需要极限并发 |

两种共用同一套活动模型；差别只在**库存与并发策略**，不是两个功能。

## 2. 当前实现（已具备）

| 能力 | 实现 |
|---|---|
| 活动价覆盖结算价 | `PromotionService.prepare` 按 `FLASH_SALE` 覆盖 |
| **原子扣减库存** | `UPDATE promotion SET sold_quantity = sold_quantity + ? WHERE id=? AND sold_quantity + ? <= stock_limit`，一条语句完成"检查+扣减" |
| 售罄拦截 | 扣减失败即 `PROMOTION_SOLD_OUT` |
| 每人限购 | `pg_advisory_xact_lock(promotion-user:…:phone)` + 已核销数校验 |
| 未支付释放 | `releaseOrder` → `decreaseSold`，名额回到池子 |
| 并发验证 | `FlashSaleConcurrencyTest`：20 线程抢 5 件 → **恰好 5 成功**，`sold_quantity=5` |

## 3. 与"真秒杀"还有的差距

| 差距 | 影响 | 方案 |
|---|---|---|
| 单行 `sold_quantity` 是热点行 | 高 QPS 下锁等待上升 | Redis 预扣（Lua 原子）+ 异步落库对账；或分桶（N 个计数器） |
| 无请求削峰 | 瞬时流量直打数据库 | 网关令牌桶 / 队列（BUCKET4J + Redis） |
| 无限流与排队页 | 抢不到时体验差 | 排队令牌 + 前端轮询 |
| 无压测基线 | 不知道能扛多少 | 压测脚本（H13） |

## 4. 实施顺序（不一次性重写）

1. **先测**：压测现有实现，得出单实例能扛的 QPS（有数据再优化）；
2. **Redis 预扣**：`DECRBY` + Lua 保证不超卖，成功后异步写 `promotion` 与 redemption；
3. **对账任务**：Redis 与数据库差异自动告警并修正（不允许静默偏差）；
4. **限流**：Bucket4j 按活动维度限流，超限返回"排队中"而非 500。

> 说明：第 1 步是前提——没有基线就优化，容易把简单问题复杂化。
