# 从 CRMEB 提炼的商城设计思路（概念级，非照搬）

> 日期：2026-10-19
> 触发：用户要求拆解 CRMEB 数据库，吸收设计思路，重点是商城常规功能、小程序对接、分销
> 方法：**clean-room**——只提炼数据模型的概念与拆分方式，不复制表名、字段名、SQL 与页面结构（项目规则 AGENTS.md §9）。
> 结论先行：CRMEB 的价值在于**功能覆盖完整、每个模块都有配套账本与状态机**，而不是表设计本身。

## 1. 商城常规功能：它覆盖了哪些概念（对照我们的现状）

| 域 | CRMEB 有的概念 | 我们的现状 | 缺口 |
|---|---|---|---|
| 商品 | SPU/SKU、规格模板、规格值、类目（多级）、品牌、商品详情（富文本）、参数、评价、收藏、浏览足迹 | SPU/SKU、选项、类目、翻译、上下架、图片 | **规格模板**、品牌、评价、收藏、足迹、参数 |
| 营销 | 优惠券（领取/使用/过期/退回）、秒杀、拼团、砍价、积分抵扣、签到、会员价、满减满折 | 优惠券（POS）、秒杀/买赠/拼团、会员等级（POS） | 线上优惠券、砍价、签到、满减满折、叠加互斥 |
| 交易 | 购物车、结算、订单状态机、订单商品快照、退款/售后、物流跟踪、地址簿 | 结算、订单状态机、售后、订单行快照（已做） | **购物车（服务端）**、地址簿、物流轨迹 |
| 内容 | 文章/公告、页面 DIY、导航、协议 | 文章（已做）、法律文档 | 导航、页面搭建 |
| 用户 | 手机/微信 openid/unionid、等级、余额、积分账本、签到、邀请关系 | 会员（POS）、分销绑定 | **openid/unionid 绑定**、余额账本、签到 |
| 支付 | 余额、微信 JSAPI/小程序、支付宝、充值 | Mock 支付 + 组合支付（POS） | 真实渠道（见支付设计） |
| 财务 | 账单流水、提现、佣金结算 | 结算单（起步）、佣金 5% 直接生成 | **账本、冻结期、提现、对账** |

**关键启发**：CRMEB 每个涉及钱的模块都配一张**流水账本**（余额、积分、佣金），而不是只改余额字段。
这与我们已定的 `cost_ledger`、`audit_event` 思路一致，应贯彻到余额与佣金。

## 2. 小程序对接：它把哪些东西放服务端

| 能力 | 服务端职责 | 我们要补的 |
|---|---|---|
| 登录 | `code` 换 `openid/session_key`；`unionid` 打通多端 | 小程序登录接口 + 用户主体（与会员共用） |
| 手机号 | 解密手机号或新版 `code` 换号，**不落明文** | 手机号加密字段 + 授权记录 |
| 支付 | 统一下单拿 `prepay_id`，返回小程序调起参数（`timeStamp/nonceStr/package/signType/paySign`） | 微信 JSAPI 适配器（在支付设计内） |
| 订阅消息 | 模板 ID、发送时机、发送结果记录 | `message_template` + 发送日志 |
| 分享/分销 | 带 `scene` 的小程序码，扫码绑定上级 | 推广码 + 绑定事件 |
| 发货 | 上传发货信息（物流公司/单号） | 物流回传接口 |

**关键启发**：小程序端要的东西都极简（参数、模板 ID、绝对图片 URL）——这也是我们已定"快照存绝对 URL"的原因。

## 3. 分销：CRMEB 的模型拆得比我们细

| 环节 | CRMEB 的做法（概念） | 我们现状 | 应补 |
|---|---|---|---|
| 关系绑定 | 首次点击/注册/下单绑定上级，**唯一上级 + 有效期** | 已有 5 种绑定模式 | 统一绑定事件与唯一性约束 |
| 层级 | 支持多级（可配置），佣金按级分配 | 单级 5% | 层级配置 + 按级计算 |
| 佣金生成 | 订单**完成后**生成，不是支付即得 | 支付后立即生成 5% | 改为"完成 + 冻结期" |
| 冻结期 | 售后窗口内冻结，超期解冻 | **无** | `commission_ledger` 状态机：FROZEN→AVAILABLE→WITHDRAWN / REVERSED |
| 退款回冲 | 退款按比例扣回佣金 | 部分实现 | 按订单行/实付比例回冲 |
| 提现 | 门槛、手续费、审核、打款、失败回滚 | **无** | 提现单 + 审核 + 打款结果 |
| 防刷 | 自购不返佣、同设备/IP 限制、互相绑定检测 | **无** | 风控规则（复用 `risk_alert`） |

**关键启发**：分销不是"算个百分比"，而是一套**账本 + 状态机 + 风控**。我们现在的 5% 直接写库，
退款时容易对不上，这是必须先改成账本的原因。

## 4. 我们应当补的表（按优先级）

| 优先级 | 表 | 作用 |
|---|---|---|
| P0 | `cart` / `cart_item` | 服务端购物车（跨端一致，登录后合并） |
| P0 | `member_address` | 地址簿（含默认地址、软删除） |
| P0 | `commission_ledger` | 佣金账本（冻结/解冻/回冲/提现）与状态机 |
| P0 | `member_balance_ledger` | 余额流水（充值/消费/退款） |
| P1 | `product_review` | 评价（订单完成后可评，含图片） |
| P1 | `member_favorite` / `browse_history` | 收藏与足迹（转化分析用） |
| P1 | `withdrawal` | 提现单 + 审核轨迹 |
| P2 | `shipping_track` | 物流轨迹（对接快递查询） |
| P2 | `message_template` / `message_log` | 订阅消息模板与发送记录 |
| P2 | `page_layout` | 首页/落地页配置（复用 `theme_config` 的 JSON 思路） |

## 5. 明确不照搬的地方

1. **金额用整数分 + 币种**（CRMEB 多为 decimal）；我们已有约束。
2. **不复制它的 DIY 页面 JSON 结构**，用我们自己的 `theme_config`，字段由后台表单生成。
3. **不复制表名/字段名**；表结构按我们的模块与 Flyway 规范重写。
4. **不做多商户 marketplace**（CRMEB 有部分多店能力），我们是自营 + 供应商代发。

## 6. 落地顺序

1. `commission_ledger` + 改造现有 5% 佣金逻辑（冻结期、回冲）——**金融正确性优先**
2. `cart` / `member_address`（下单链路的常规能力）
3. 小程序登录 + 手机号 + 订阅消息
4. 评价、收藏、足迹
5. 提现与提现审核
