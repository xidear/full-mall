# ADR-0012: POS 收银、组合支付与现金财务

- 状态：Accepted（设计）
- 日期：2026-10-18

## 背景

门店收银不是“在线支付接口的门店版”。它包含组合支付、现金找零、积分/优惠券核销、会员储值、班次现金小结、支付渠道对账、退款/作废、离线降级和硬件（扫码枪、钱箱、NFC/碰一碰、打印机）。这些能力必须独立成 bounded context，不能复用线上订单支付的状态机硬套。

## 决策

- 新增 `pos` 业务上下文，与线上订单/支付分开；POS 销售单可以关联线上订单（O2O 核销），但不是同一个聚合。
- 组合支付采用 `PosSale + PosTender[]`：
  - 应收 = 商品小计 - 优惠 - 券 - 积分抵扣；
  - 实收 = sum(tenders)；
  - 现金找零单独记录。
- 积分、储值、优惠券使用不可变 ledger；余额只是投影，禁止直接改余额。
- 现金管理使用班次（shift）+ 现金流水：开班备用金、现金收付、退款、交接、关班实盘、差异审批。
- 支付厂商采用 `PosPaymentProvider` SPI + 独立 adapter module；核心只依赖 `payment-api`。
- Java 依赖管理使用 Maven（Gradle 可选），Maven Central + BOM/版本锁定 + SBOM/License 扫描；不引入 OSGi。
- 需要热插拔时优先独立 adapter 服务，不把厂商 SDK 塞进核心领域。
- 碰一碰/银行卡/扫码依赖认证终端和收单资质；后端只负责意图、查询、回调、退款、对账，不能假设纯软件可实现。
- 开源默认 Mock provider；真实 provider 由配置和证书启用，密钥不入库/不入 Git。

## 后果

- POS 需要独立的数据表、状态机、权限、审计和财务口径。
- 组合支付和退款必须能按 tender 维度回滚；不能只记一个“已支付”按钮。
- 现金差异、积分/券负债、支付渠道应到账/实到账必须可对账。
- 硬件/资质是项目外部依赖，必须提前申请，不能用代码绕过。
- 实现顺序：Mock 组合支付闭环 → 真实扫码/聚合支付 → 碰一碰/终端认证 → 财务对账与储值。
