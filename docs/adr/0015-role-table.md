# ADR-0015：角色落表（role），权限矩阵不再依赖硬编码角色

- 状态：已采纳（2026-10-30）
- 相关：AGENTS §7（禁自建字段权限矩阵）、§9（单一来源）、§13（枚举必须可选）

## 背景

角色此前是散落在 6 处的字符串常量（权限矩阵、鉴权过滤器、门店范围、前端页签、标签映射、
POS/店长授权），其中三处已在本轮收敛到 `StaffRoles`。但**权限矩阵仍只能配置固定角色**：
`permission` 表存权限字典、`role_permission` 存映射，而"有哪些角色"没有任何表，
新增角色要改代码 + 改前端页签。

另有一个真实缺陷：矩阵页的 STORE / CS 页签保存的是**永不生效的数据**——权限过滤器只作用于
`/admin/**`，而这两个角色被拒于 `/admin` 之外。

## 候选

| 候选 | 结论 | 理由 |
|---|---|---|
| 维持硬编码枚举 | 不采用 | 新增角色要改代码+前端；前端页签会与后端再次漂移 |
| **role 表 + staff_user.role 外键** | **采用** | 与 `permission`/`role_permission` 同构；角色成为数据，可由矩阵页管理；外键挡住"写了不存在的角色" |
| jCasbin（已在技术决策中评估过） | 暂不采用 | 引入策略引擎对当前"功能级 RBAC"是过度设计；需要 ABAC/复杂策略时再评估 |

## 决定

1. 新增 `role(code PK, label, editable, sort_order)`，播种 5 个角色；
2. `staff_user.role` 增加外键引用 `role(code)`（原来只有 CHECK）；
3. `editable` 表示该角色的权限可在矩阵里配置：ADMIN 为 `false`（恒有全部权限，由代码短路）；
4. `PermissionService` 的可编辑角色**从表里读**，不再用常量；
5. 角色标签由后端下发（`label`），前端不再维护一份 `roleLabels`。

## 迁移

项目未上线，迁移已收敛为单一基线 `V1__baseline.sql`：本次直接改基线，不新增增量迁移。

## 风险与后续

- 删除角色前必须检查是否仍有员工在用（外键会拦住，返回 409 需要显式实现，当前是 500 级
  `DataIntegrityViolation`）——这是下一步；
- 前端页签目前仍写死 4 项，需改为读 `matrix.roles`（后端已返回可编辑角色）。
