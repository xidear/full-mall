# 匿名（游客）下单的使用场景与收银台方案

> 结论先行：**线上不保留"匿名下单"**。中国大陆的线上交易必须绑定真人（手机号实名 + 可追溯）。
> 现有"游客下单"能力只保留为**线下面对面交易的辅助**，并通过收银台（POS）完成。

## 1. 现有实现 vs 目标

| 现状 | 说明 |
|---|---|
| 线上 `POST /api/v1/checkout` 允许不带会员登录，只填联系人手机号 | 手机号即自然人凭证，但没有强校验（不验证码即算通过） |
| 游客订单靠 `orderId` + `contact_phone` 查询（履约/物流） | 已加归属校验（第 112 轮） |

**目标**：所有订单都必须绑定一个可追溯的自然人标识。

## 2. 用户要求与现实约束（中国大陆）

- 线上下单必须真人：手机号是事实上的实名载体（微信/支付宝支付本身也需实名）。
- 因此"完全匿名"不应作为产品能力提供，只存在**"未注册但已填手机号"**的顾客（访客）。
- 访客与匿名是两件事：**访客有手机号**，可追溯；**匿名没有**，不可追溯 → 不做。

## 3. 三种场景与对应方案

### 场景 A：收银台面对面交易（最常见）

顾客在店内、当场付款带走商品。

**方案**：`POS` 销售单，**无需物流、无需匿名下单**。
- 已有实现：`/store/v1/pos/sales`，支持会员/优惠券/组合支付/退款。
- 未识别会员时，收银员可录入手机号建立会员（已有会员创建能力），而不是走"游客下单"。

### 场景 B：收银台预定 / 预购（到货自提）

顾客在店内预定，货到后到店取；或门店帮顾客下单寄送。

**方案**：收银台代下单（`created_by=CASHIER`），顾客信息由收银员录入手机号；
- 到货后**短信通知顾客到店自提**（现有 `SMS` 通道 + `ORDER_*` 事件）；
- 门店工作台看到"待自提"列表（已有 `/store/v1/pickups/...`）。

这样"顾客没有线上账号"也不影响流程，且全程可追溯（收银员 + 顾客手机号）。

### 场景 C：顾客线上下单但没注册

**方案**：允许**访客下单**（手机号必填 + 短信验证码校验），下单后自动创建会员（现有 OTP 登录已具备自动建会员能力）。
- 效果：既满足"不注册也能买"，又保证每单绑定一个可追溯的会员主体；
- 订单归属用 `member_id`（现有 `attachMemberByPhone` 已支持），不再依赖"知道订单号就能查"。

## 4. 需要的改动（按优先级）

| 项 | 说明 | 状态 |
|---|---|---|
| 线上 checkout 强制短信验证码 | 手机号必须通过 OTP 校验（或登录态会员） | ⬜ 待实现 |
| 下单即建会员/绑定 | 复用 OTP 登录的建会员逻辑 | 部分具备（按手机号绑定） |
| 收银台代下单记录操作员 | POS 已有 `cashierName`，后台代下单需补 | ⬜ |
| 移除"匿名订单凭订单号可查" | 已改为订单号 + 手机号 / 会员本人 | ✅ 已完成 |

## 5. 为什么不在线上保留匿名

- 无法追溯：纠纷、退款、风控都失去主体；
- 与支付实名要求冲突：微信/支付宝支付本身需要实名；
- 安全：匿名 + 订单号可查 = 自提码泄露（第 112 轮已见识过这类问题）。

## 6. 结论

1. **POS 面对面**：不涉及匿名，也不需要物流。
2. **POS 预定/预购**：收银员代下单 + 短信通知自提，顾客无需账号。
3. **线上未注册**：访客下单 + 手机号 OTP 校验 + 自动建会员，"访客"替代"匿名"。
4. 真正的"匿名"不提供。
