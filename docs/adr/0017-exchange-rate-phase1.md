# ADR-0017：汇率（手工 + 自动拉取 + 精确换算）

- 状态：已采纳（2026-10-31）
- 关联：ADR-0004（金额与币种）、`docs/CROSS_BORDER_READINESS_AUDIT.md`（P0-5）

## 背景

ADR-0004 曾承诺 `ExchangeRateProvider`，但仓库一直没有实现；多币种只能靠“每个市场人工定价”。
跨币种退款、分账与报价都缺少一个可核对的换算依据。

完整方案（自动拉取汇率、下单快照、结算按汇率重算）涉及订单表结构、支付报文与财务对账，
不适合在本轮直接铺开。按“好做就做、但不隐式改钱”的原则，先做阶段 1。

## 决策（阶段 1）

1. **汇率表** `exchange_rate`：`base_currency / quote_currency / rate(numeric 20,10) /
   source / effective_at / created_by`；同一币种对允许保存历史，同一生效时刻唯一。
2. **换算规则**：`1 base = rate quote`，全程 BigDecimal：
   最小单位 → 主单位 → ×汇率 → 目标最小单位，`HALF_UP` 到目标币种小数位。
   小数位来自 `CurrencyPrecision`（ISO-4217）。
3. **只允许反向推导**：没有 A→B 时可用 B→A 取倒数；**不做多跳三角换算**（中间币种无业务依据，
   且两次舍入会引入误差）。找不到汇率明确 `EXCHANGE_RATE_NOT_FOUND`，不按 1:1 兜底。
4. **管理接口**：`/admin/v1/exchange-rates`（列表/新增/删除）与 `/convert`（最小单位进、最小单位出）；
   权限与系统设置一致（`settings.manage`），新增/删除写审计。
5. **不接自动改价**：商品价仍按市场定价；订单金额不回算；结算/退款不改变原币种金额。
6. **下单汇率快照（V6）**：订单写入 `fx_rate / fx_base_currency / fx_base_total_amount /
   fx_rate_at`；只记录“订单币种→基准币种（`app.fx.base-currency`，默认 CNY）”的事实。
   无可用汇率时**不阻塞下单**，但写审计 `ORDER_FX_RATE_MISSING`，后台订单详情显示“未快照”，
   不允许把缺失当成汇率 1。
7. **退款允许不同汇率（V7）**：退款金额始终是**原订单币种**，不做跨币种退款/分账；
   `order_line_refund` 记录退款时点的 `fx_rate/fx_base_amount/fx_rate_at`，允许与下单快照不同。
8. **自动汇率（阶段 2）**：
   - 供应商通过「第三方服务 → 自动汇率」配置，当前支持免费无 Key 的 **Frankfurter（ECB）** 与演示 **mock**；
   - **不在数据库里保存 API Key**（当前供应商不需要）；未来需要 Key 的供应商走环境变量/密钥管理，不写库；
   - 演示/开发模式（`app.mode=demo/dev`）未配置时显式使用 mock；生产（`prod`）未配置则**不自动拉取**，
     继续使用手工汇率，应用照常启动；
   - 配置后拉取失败：**保留上次自动/手工汇率**，只记录失败原因；成功才写入新汇率；
   - 自动拉取由定时任务触发（默认 1 小时），也可在后台「汇率」页点「立即拉取」。
9. **只做直接汇率**：provider 返回什么就存什么；没有 A→B 时只允许用 B→A 反向推导。
   “多跳三角换算”指 A→B→C 两次换汇（会引入两次舍入且中间币种无业务依据），**明确不做**。

## 明确未做

- 跨币种退款/分账（用户明确不允许）：退款只按原币种。
- 多跳三角换算（明确不做，只做直接汇率 + 反向推导）。
- 自动汇率的偏差告警（当前只记录上次成功/失败状态）。

## 后果

- 运营可以维护“某日某对币种”的汇率，并用同一套 BigDecimal 逻辑验证报价/客服口径。
- 金额精度（币种小数位）与汇率换算共用 `CurrencyPrecision`，不会出现 JPY 被 ×100 的问题。
- 阶段 2 的下单快照已落地：订单表保存汇率与基准币种总额，报表/对账可直接用，无需回算。
