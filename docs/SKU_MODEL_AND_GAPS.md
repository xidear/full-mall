# SKU 模型现状与缺口（多规格 / 多维度 / 单件追踪）

> 触发：批量改价是否考虑多规格？多维度组合、缺货差异、门店仓库"具体个体"如何处理。

## 1. 现状：最小可售单位就是 SKU

| 环节 | 粒度 | 说明 |
|---|---|---|
| 价格 | **SKU** | `sku.price_amount`，每个规格可不同价 |
| 库存 | SKU + 批次 | `inventory_batch(sku_id, batch_no, quantity, expiry)` |
| 成本 | SKU（批次加权） | `sku_cost` + `stock_cost_movement` |
| 促销范围 | SKU / 类目 / 全场 | `rules.scope` + `skuId` |
| 订单行 | SKU | `order_line.sku_id` + 快照 |
| 拣货 | 批次 | `pick_task_line(batch_id)`，合并行靠映射表回填 |
| 售后 | 订单行 → 原批次 | 退货按原批次成本回冲 |

**结论**：交易链路本身就是按 SKU 走的，多规格不同价在数据层没有问题。

## 2. 批量改价：已支持"每个 SKU 不同价"，但表达方式不够

- 现有接口 `POST /admin/v1/products/skus/batch-price`：body 是 `[{skuId, priceAmount}]` → **逐 SKU 定价，天然支持不同规格不同价**；
- 整批语义：任一 SKU 不存在或价格 ≤0 → 整批失败，不改任何价格；
- **缺口**：
  1. 没有后台界面（只能调接口）；
  2. 没有"按规格维度筛选后批量改"（例如"所有 256G 涨 100 元"）；
  3. 没有"按比例调整"（如全线 +5%）与预览确认。

## 3. 多维度规格（颜色 × 内存 × 存储）：当前只支持单维生成

`sku.options_json` 是 JSONB，**结构上能存多维**：

```json
{"颜色":"黑","内存":"12G","存储":"256G"}
```

但矩阵生成工具（F6）**只写一个键**：

```sql
jsonb_build_object(:optionName, :value)   -- 单维度
```

**缺口**：缺少"多维笛卡尔积生成 + 组合级禁用（某组合不生产/不售卖）"。

## 4. 缺货与库存不一致：SKU 级已成立，但前台展示需明确

- 某组合缺货 = 该 SKU 库存 0（或批次全过期），**不影响其它规格**；
- 商品详情需返回每个 SKU 的可售数量/是否缺货，前端禁用不可选组合（当前接口返回 SKU 列表，未标 `available`）；
- 库存不一致是常态，按 SKU + 批次独立扣减，不存在"规格共用库存"。

## 5. 门店/仓库的"具体个体"：**当前没有单件追踪**

| 需求 | 现状 |
|---|---|
| 序列号/IMEI/唯一码 | ❌ 无 `serial` 表 |
| 入库逐件登记 | ❌ 只有批次数量 |
| 拣货扫码校验具体件 | ❌ 只有批次 |
| 售后按序列号追溯 | ❌ 只能追到批次 |
| 3C/手机类目要求 | 需要单件（IMEI）管理 |

这是真实缺口：**手机这类商品，只到批次级别无法处理"哪台机子保修、哪台被换过"**。

## 6. 建议实施顺序

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 多维规格生成（笛卡尔积 + 禁用组合） | 手机/服饰都必需，改动集中在生成与编辑 |
| P0 | 批量改价 UI（勾选 SKU、按维度筛选、预览后提交） | 接口已有，缺可用入口 |
| P1 | 商品详情返回 SKU `available` + 缺货标记 | 前台体验与防超卖 |
| P1 | 单件序列号：`serial` 表 + 入库登记 + 拣货扫描 + 售后按序列号查 | 3C 类必需，工作量大，需单独排期 |
| P2 | 按比例调价、价格审批留痕 | 运营效率与合规 |

## 7. 需要你确认

1. **是否现在就要单件（IMEI/序列号）管理**？这决定要不要建 `serial` 表与扫码流程（约 1–2 轮）。
2. 多维规格最多几维（3 维足够？），是否需要"组合禁用"。
3. 批量改价是否需要审批留痕（谁改的、改前改后）。
