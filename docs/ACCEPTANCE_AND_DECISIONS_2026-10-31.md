## 二、反问清单（如果当时问你，我会这么问）

### Q1. 15052 应该跑「开发服务器」还是「生产构建」？

- **A. Vite dev（最终选择）**：改代码即热更新，开发阶段速度优先；代价是 15052 暴露源码、
  依赖浏览器实时编译、没有构建期类型检查。
- **B. `vite preview` 提供 `dist`**：与生产同源代理，构建期跑 `vue-tsc`；改代码后必须重新 build。
  已保留为上线前切换方案（`scripts/admin-preview.sh`）。
- **C. nginx 静态托管 + 反代**：最接近生产，但需要改运维 compose/证书，超出本阶段。

**最终选择 A**：当前是开发阶段，以迭代速度为主；生产阶段再用 `scripts/admin-preview.sh` 切
构建产物。两个脚本都占用 41281，不会同时跑。

### Q2. 真实模型用「本机 9B」还是「免费云端」？

- **A. 本机 Ollama + qwen 9B**：数据不出内网；宿主机有 NVIDIA 内核模块，但当前执行环境没有
  `/dev/nvidia*` 设备节点；9B 即使有 GPU 也要额外权重/显存/并发运维，性价比低。
- **B. 公司自营 OpenAI 兼容端点 `deepseek-v4.1-flash`（已选）**：本机网络内、无需 Key、实测 200、
  与现有 `openai-chat` 适配器零改造；代价是依赖该端点可用性（不可用→503，不影响下单）。
- **C. OpenRouter / OpenCode 等免费模型**：免费但需账号/Key，配额与可用性随活动变化，数据出境。

**选择 B**：在“真实、可复现、免费”三个条件里 B 同时满足；后台「模型供应商」可随时换成
任意 OpenAI 兼容模型（含本地推理），不需要改代码。

### Q3. 检索用「语义」还是「关键词」？

- **A. SEMANTIC + 本机 CPU embedding（最终选择）**：新增 `tools/embedding-service`
  （端口 41291，`Xenova/bge-small-zh-v1.5`，512 维，量化 ONNX，CPU 可跑），把
  `local-embedding` 配成 `openai-embedding` 供应商，`APP_AI_ASK_RETRIEVAL=SEMANTIC`；
  已实测「运费怎么算」召回 0.777 并由模型作答。
- **B. 只用 KEYWORD**：零外部依赖；文档型知识召回弱。保留为没有 embedding 时的显式模式。
- **C. 失败自动降级 KEYWORD**：违反“禁止静默兜底”，禁止。

**最终选择 A**：本机 24 核 CPU 跑 512 维小模型足够（毫秒级），语义检索真正可用；
embedding 服务不可用时仍明确 503，不会偷偷退回关键词。

### Q4. 门店“停用”还是“删除”？

- **A. 物理删除**：列表干净；但订单、库存批次、POS 班次都引用门店，删除会留下悬空引用。
- **B. `active` 启停（最终选择）**：可逆、保留历史；代价是列表需要「全部状态」筛选。
- **C. 启停 + 软删除**：在 `active` 之外再加 `deleted_at`，用于“关店且不再维护”的长期归档。

**最终选择 B**：当前没有“必须彻底隐藏”的业务诉求，`active` 已覆盖停业/不可选；
软删除会引入第二套“存在性”语义（每个查询都要记得排除），等确有长期归档需求再加，
届时用 `deleted_at` 而不是物理删除。

### Q5. 进行中的促销能不能直接编辑？

- **A. 允许直接改**：运营改价最快；但用户看到的价与结算价会在眼皮下变化，出问题无法归因。**不选**。
- **B. 只允许改草稿 + 复制为草稿（已选）**：改活动先结束旧活动、改副本再启用；多一步操作，换来可追溯。
- **C. 加审批流**：最严谨，但当前没有审批中心，成本过高。

**选择 B 的原因**：促销是价格承诺，必须可追溯；“复制为草稿”把多出来的那一步变成一次点击。

### Q6. 数据库升级：重建还是增量迁移？

- **A. 开发阶段允许重建库**：最简单，但会丢演示/联调数据，且容易把“迁移写错”掩盖成“重建就好”。
- **B. 增量迁移 `V3__store_admin.sql`（最终选择）**：不删数据，Flyway 记录版本；已在本机验证 V3 成功。
- **C. 改 baseline**：会让旧库 checksum 失配，启动即炸。**禁止**。

**最终选择 B**：开发阶段“允许重建”，但非必要不重建；只有 baseline 变更或迁移不可修复时才重建。
注意：**V1/V2 squash 之前的旧库**仍不支持原地升级，需要重建（已写进交接）。

### Q7. 跨云迁移做不做？

- **A. 本批做**：需要对象存储/数据库/消息队列三套迁移与回滚演练，工期不可控。**不做**。
- **B. 只写规划（已选）**：明确前置条件、回滚与触发条件，避免以后把“改 endpoint”当迁移。
- **C. 完全不提**：下次又会从零讨论。**不选**。

**选择 B 的原因**：用户明确“先作为将来的规划”，规划落地成 `docs/CROSS_CLOUD_MIGRATION_PLAN.md`，
代码层不引入半成品。
