# 保质期：现状与边界（业务真正关心的点）

> 结论先说：**保质期已经实现，且不需要序列号**。序列号是可选能力，不围绕它做大投入。

## 已实现（可直接用）

| 能力 | 位置 | 说明 |
|---|---|---|
| 批次级保质期 | `inventory_batch.expiry_date` | 收货时登记，缺失则允许为空（非生鲜） |
| **FEFO 先进先出** | 拣货/预占 `ORDER BY expiry_date ASC NULLS LAST` | 先到期的先出 |
| **过期禁止出库** | 预占条件 `expiry_date IS NULL OR expiry_date >= ?` | 过期批次不参与分配 |
| 临期状态 | `inventory_batch.status = NEAR_EXPIRY` | 参与可售判断，可被规则降级 |
| 临期查询 | `findBatches(..., expiringInDays)` | 可查"未来 N 天内到期"的批次 |
| 商品保质期策略 | `sku.shelf_life_policy_json` | 不同商品不同规则 |
| 盘点/发货带出 | 拣货行、批次视图均含 `expiryDate` | 一线作业时可见 |

## 不需要序列号的原因

- 生鲜/食品靠**批次 + 到期日**即可完成先进先出与过期拦截；
- 序列号只在"单件唯一、需逐件保修"的 3C 场景才有意义；
- 你已明确：不围绕序列号大费周折 → 现有能力保留（登记/绑定/批次清单），**不做按号追人查询**。

## 仍可补的两件小事（按需）

| 事项 | 说明 |
|---|---|
| 临期预警任务 | 每天扫"30/7/1 天内到期"批次，推给门店/仓库（可复用现有通知通道） |
| 过期自动下架 | 到期日次日把批次状态置为 `EXPIRED` 并剔除可售（当前靠查询条件兜住） |
