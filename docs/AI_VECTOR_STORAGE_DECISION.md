# 向量存储与检索技术路线（ADR-001）

> 回答两个具体问题：为什么嵌入式测试库没有 pgvector；"10 万"到底指什么、什么规模该换方案。

## 1. 为什么嵌入式测试库没有 pgvector

**不是硬件问题，也不是版本不匹配，是"扩展没被打包"。**

| 事实 | 说明 |
|---|---|
| pgvector 是 PostgreSQL 的 **C 扩展** | 需要针对**具体 PG 大版本**编译出 `vector.so`，安装到 `$PGHOME/lib`，再 `CREATE EXTENSION vector` |
| 测试用的是 zonky `EmbeddedPostgres` | 它下载的是 PostgreSQL **官方发行二进制**，只含核心功能；pgvector 不在其中 |
| 换 Docker 镜像就能有 | 官方镜像 `pgvector/pgvector:pg16` 自带扩展；但本机**没有 Docker**，CI 也没有 |
| 自己编译不可取 | 要匹配 PG 版本头文件 + 编译工具链，升级 PG 就得重编，属于把运维复杂度塞进测试环境 |

结论：**测试环境缺的是扩展二进制，不是能力上限**。生产库只要装一次 `CREATE EXTENSION vector` 就有。

## 2. "10 万块" 指的是知识块数量，不是钱

原文表述有歧义，这里纠正：**10 万 = 100,000 个知识块（chunk）**，与服务器价格无关。

按 1024 维 float32 估算：

| 块数 | 向量原始体积 | 说明 |
|---|---|---|
| 1 万 | ≈ 41 MB | 随便存 |
| 10 万 | ≈ 410 MB | 当前方案的分界点 |
| 100 万 | ≈ 4.1 GB | 必须上 ANN 索引 |

## 3. 本机实测（决定阈值的依据）

`VectorScaleBenchmarkTest`（本机，2026-10-19）：

```
维度 256、10 万块、暴力余弦：54 ms/次查询
按 1024 维折算：约 216 ms/次查询
```

注意：这**不是**我们生产路径的耗时——生产是"关键词先缩到 200 条候选，再做余弦重排"，
候选集小两个数量级，单次重排 < 5 ms。全表暴力只有在**没有关键词命中过滤**时才会发生。

## 4. 三条可选路线

| 路线 | 优点 | 代价 | 适用 |
|---|---|---|---|
| **A. 现状：关键词候选 + 应用内余弦** | 零扩展依赖、测试与生产一致、可解释（能看出命中哪个词） | 依赖关键词命中；同义改写召回差 | ≤ 20 万块，且问题里含商品名/术语 |
| **B. pgvector（生产库装扩展）** | SQL 内 ANN 索引、可与元数据过滤下推 | 测试环境需 Docker 或独立 PG；运维多一项扩展管理 | > 20 万块，或需要复杂 SQL 过滤 |
| **C. Apache Lucene HNSW（纯 Java）** | 无数据库依赖、测试/生产同一套、成熟（Lucene 9+） | 索引与数据双写一致性要自己保证 | 需要语义召回但不想动数据库 |

## 5. 决策

1. **现在保持 A**：实测够用，且与演示/测试环境一致，不引入无法在 CI 验证的依赖；
2. **触发升级的条件**（写死，避免拍脑袋）：
   - 知识块 > **20 万**；
   - 或线上"同义改写问法"召回失败率 > 20%（用评测脚本量）；
   - 或单次问答检索耗时 P95 > 300 ms。
3. **升级首选 C（Lucene HNSW）**：因为我们的测试环境没有 Docker，
   B 会让"测试和生产不一致"——这正是本项目反复踩过的坑；C 能在 CI 里真跑。
4. 若客户环境已有 pgvector 且坚持 SQL 侧过滤，再走 B，并在 `docs/AI_SERVICE_MODULE.md` 记录该客户的差异。

## 6. 这件事的教训

上一轮我写"超出 10 万块再切 pgvector"，把**结论**写成了**依据**：既没说清为什么测试库没有扩展，
也没给出量化阈值。这份 ADR 补上：现象 → 原因 → 实测 → 选项 → 触发条件。

## 7. pgvector 落地预案（等真机解除 Docker 限制后实施）

用户决定：**先把当前功能做完，迁移到真机并解除 Docker 限制后再上 pgvector**。以下为待执行清单。

| 步骤 | 内容 |
|---|---|
| 1 | 生产库 `CREATE EXTENSION vector`（PG 15/16 官方镜像或 `pgvector/pgvector`） |
| 2 | 迁移 V76：`ALTER TABLE knowledge_chunk ADD COLUMN embedding_vec vector(1024)` + HNSW 索引（`vector_cosine_ops`） |
| 3 | 回填：把现有 `embedding`（bytea）转成 `embedding_vec`（一次性脚本） |
| 4 | 新增 `PgVectorKnowledgeStore`：`ORDER BY embedding_vec <=> ?::vector LIMIT ?`，保留元数据过滤 |
| 5 | 开关：`app.ai.store=bytea|pgvector`；两实现共用同一 `KnowledgeStore` 端口，测试各覆盖一次 |
| 6 | 测试环境：Testcontainers `pgvector/pgvector:pg16`；CI 无 Docker 时**跳过该用例并显式标注**（不是静默跳过） |
| 7 | 评测：同一批 50 条标注问题，对比关键词 vs 向量 Top-3 命中率 |

**验收**：向量检索 Top-3 命中率比关键词提升 ≥ 15 个百分点；检索 P95 < 100ms（10 万块）；两套实现结果集结构一致。
